== Tcl/Tk (the macOS blocker)

* The osx-arm64 `swift-t-r` 1.6.9 package needs `tk>=8.6.15,<9.0a0`.
  The pin is in `swift-t/dev/conda/osx-arm64/deps.sh` (line 27,
  `SPEC_TK`).
* The pin exists because tk 8.6.13 builds `-h892fb3f_3`, `-hd3d0363_3`,
  and `-h010d191_3` export `strstr`. On macOS, that makes Turbine's
  `libtclturbine` bind `_strstr` to Tcl instead of libc, and it fails at
  runtime with "Symbol not found: _strstr". `tk-8.6.13-hbeba79b_4` and
  `tk-8.6.15-*` are fine. The comment in `deps.sh` (around lines 28–60)
  explains this.
* Channels for osx-arm64 `tk`:
  - conda-forge: 8.6.10, 8.6.11, 8.6.12, 8.6.13, 9.0.4. No 8.6.15.
  - defaults (anaconda.org): 8.6.10, 8.6.11, 8.6.12, 8.6.14, 8.6.15, 9.0.4.
  - swift-t channel: no `tk` packages.
* So `tk>=8.6.15` exists only in `defaults`. Miniforge (conda-forge only)
  cannot solve it. Miniconda includes `defaults`, so it can.
* Do NOT just pin `tk==8.6.13` to get the solve working. That can select
  the `_3` builds that break `strstr`.
* Safe builds (per the `deps.sh` comment; `strstr` export not verified
  by `nm`):
  - conda-forge `tk 8.6.13 hbeba79b_4`. Pin with
    `SPEC_TK='tk==8.6.13=hbeba79b_4'`. This is the build the local
    Linux-built and tested osx package resolved to. It is on conda-forge,
    so Miniforge can use it. It does NOT meet the current `>=8.6.15`
    floor in `deps.sh`, so that floor must change.
  - defaults `tk 8.6.15 hcd8a7d5_0`. Meets the current floor. Only on
    `defaults`, so it needs `-c defaults` (Miniforge cannot use it).
    Build string not individually confirmed against the comment table.
* Bad builds to exclude (export `strstr`): `tk 8.6.13` with `h892fb3f_2`,
  `h892fb3f_3`, `hd3d0363_3`, `h010d191_3`. Do not use unpinned `tk`
  in the recipe; the solver may choose a bad `_3` build.
* Other available builds, not yet assessed: defaults `8.6.14`
  (`h6ba3021_0`, `h6ba3021_1`); conda-forge `8.6.13 hb31c410_0`,
  `h5083fa2_1`. tk 9.0.4 is excluded by the `<9.0a0` upper bound.
* Before changing the recipe, check the chosen package with `nm` for
  `strstr`. That needs a download (not an install); not yet done.
* Options: (a) add `defaults` to the Miniforge install, so the solve can
  reach `tk` 8.6.15; (b) rebuild the osx-arm64 package with a `tk` that
  conda-forge has and that is not the broken `_3`/_4 pattern; (c) fix the
  two-level namespace issue at the source (`turbine/code/Makefile.in`,
  `MAC_FLAT`, and the `-ltcl8.6` link order), as the deps.sh comment
  describes.

== Mac rebuild (what to do on a Mac)

1. Clone the tutorial repo and check out `swift-t` at `4b3882df1` or later.
2. Make the release tarball in Mac mode:
   `cd swift-t && dev/release/make-release-pkg.zsh -m`
   (writes `$TMP/distro`, default `/tmp/distro`, using `TMP` if set).
3. Build the osx-arm64 package from `swift-t`, with a conda that has
   `conda-build`:
   `dev/conda/conda-build.sh -r 4.4 osx-arm64 <BUILD_NUMBER>`
   Use a build number above any existing osx-arm64 build
   (the channel has 311_3..5, 312_3..5, 313_4..7, 314_2..4).
   The recipe needs `tk>=8.6.15`, which may require `defaults` in the
   build channels (not checked).
4. Test the package in a fresh env:
   `dev/conda/conda-install.sh -r <PKG>`, then
   `tests/test-swift-t.sh -E 3.13` (or other versions).
   Check `strstr`: `swift-t -v` and a trace must run without
   "Symbol not found".
5. Upload (only after tests pass, needs `anaconda login` as `swift-t`):
   `dev/conda/upload.sh <PKG>`.
   Upload is a shared-channel change: ask first.
